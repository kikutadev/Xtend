## Xtend本体：Xタイムラインの操作前先読み（ベータ実装・検証中）

**ゴール：** Xホームで「For you」と「Following」の行き来を最優先し、**スワイプする前に隣のタイムラインを準備**する。スワイプ確定後のクリックを160ms前倒しするだけでは達成とみなさない。投稿の鮮度、選択状態、各タイムラインのスクロール位置、X標準動作、拡張機能を維持する。X APIの独自保存・改変は禁止。

**方式検証：** まず、1つのWebViewでXの標準タブを一度読み込んで戻す方式が、ユーザーの画面・操作を邪魔せず、次の表示を速めるか確かめる。前の表示を凍結する方式は入力遮断や描画停滞が起きないかも確認する。効果が弱い／危険なら、2つのWebViewでタブごとのX状態を保持する方式を試験実装し、追加プロセスの物理メモリ・通信量・CPU・動画再生・設定反映を比較して判断する。Xの内部キャッシュが切替後も保持されるかは未確認。メモリ増加だけを許容条件にせず、利用可能な実機での安定性を受入条件とする。

**計測と受入：** 修正前後の「スワイプ確定→Xのタブクリック」「確定→タブ選択」「確定→投稿表示」を同条件で複数回測定する。キャンセル、連続スワイプ、スクロール、設定UI、戻る操作、拡張機能との競合を回帰確認し、メモリ負荷を悪化させない。実Xの計測結果と模擬DOMによる試験結果は分けて記録する。

**実装と測定（2026-10-26）：** ホームのスワイプ確定時にX自身のタブを160ms待たずにクリックし、WebKitのView Transitionで旧画面を短く表示する実験を別ブランチに実装。PlaywrightのヘッドレスWebKit上の合成X風ページで各8回、操作確定→タブクリック中央値 161ms→2ms、投稿反映中央値253ms→101ms（テストページ内の90ms擬似描画待ち）。2往復、キャンセル、短距離ジェスチャー、後片付けを確認。iOS Simulator向けビルドは成功。これは実Xの通信やiOS WebView実測ではなく、常時先読み実装でもない。

**実X検証（2026-10-26）：** iPhone 17 Pro / iOS 26.4のログイン済みSimulator上で、にゃっとランド併用のXtendをヘッドレスXCUITestで操作。最初の既存テストではXの左メニューが開いたままでも成功になる偽陽性を発見した。ショートカット案内と左メニューを閉じてから実Xの`For you → Following → For you`をスワイプし、双方の実タブ選択状態（XCUITestの`isSelected`）とタイムライン画像を確認。`testTimelineSwitchOnActualX`は1件成功。

**追加検証上の注意：** 既存の長い`testSwipeNavigationOnLoggedInX`を強化して専用テストと連続実行した際、UITest Runnerが`Test crashed with signal kill`で終了。新規の`testTimelineSwitchOnActualX`自体は成功。原因（アプリ・Runner・Simulator負荷）は未特定で、アプリのクラッシュと断定しない。従来テストの長さと不安定さを増やす変更は採用せず、専用テストでタブ選択を検証する。

**メモリA/B（2026-10-26）：** MacのヘッドレスPlaywright WebKitで、同じ模擬タイムラインを表示し、変更前/後それぞれブラウザを新規起動して24回往復切り替え。`before → after → after → before → before → after`の計6回。各3回の中央値はWebKit試験プロセスのRSSで117.3→117.5 MiB（切り替え後）、`footprint`で確認した同プロセスの物理フットプリントは20→20 MiB、ピーク23→23 MiB。いずれも単一のWebKit試験プロセスの数値であり、iOSのXtend/別プロセスのWebKit/実Xの使用量ではない。明確な差は検出できなかった。再実行は`scripts/measure-webkit-memory.mjs`を参照。実Xログイン済みのSimulatorは別作業のXCUITestが稼働しており、起動アプリを差し替えて行う実XのA/B測定は未実施。

**スワイプ前の先読み方式の実験（2026-10-26）：** 1 WebView内でXのタブを先にクリックして戻す方式をWebKitの合成ページで試験。`document.startViewTransition(async ...)`の処理待機中にも読み込み中の画面が表示されたため、このままでは表示中のタイムラインを保てず、不採用。次に既存Xセッションを共有する第二WKWebViewを表側ブラウザーの下に置く`--xtend-probe-preload`（DEBUGビルド専用）を試作。iPhone 17 Pro Simulatorの実Xで、第二WebViewは`/home`の`Following`が選択された状態になり、14件の投稿セルが存在することをログで確認した。ただし**見えているWebViewとの瞬時切り替え処理は未実装**。開始直後の一測定では、Xtend＋WebContentの物理フットプリントが1 WebViewで約339 MB（27+313 MB、表示値丸めあり）、2 WebViewで約705 MB（35+304+366 MB）、差は約366 MB。Networkingは除外。共有Simulatorの別作業によるアプリ差し替えで、その後の繰り返し測定は成立しなかったので比較から除外。単発結果であって実機メモリ限界の判断には使わない。二重のXページが独立してJS実行・動画・通信を行う懸念もあり、現時点では通常起動で先読みを有効化しない。

**ベータ実装・安定化（2026-10-26）：** 設定画面に初期オフの先読みスイッチを設置。Xホームのもう一方のタイムラインを第二WebViewで準備し、完了後はタップ・スワイプをネイティブのView交換へルーティングする。裏画面はタッチ・アクセシビリティを無効化し、離脱・バックグラウンド・メモリ警告では解放する。準備に失敗した場合は従来のXタブ操作へ戻す。Xの遅いReactタブ生成を再試行する仕組み、待機側のオーバーレイを閉じる仕組み、切替時のループを制限する仕組みを追加。Playwright WebKitのベータブリッジ試験およびiOS Simulatorビルド成功。実Xで第二WebViewの先読み完了とテスト引数によるネイティブ交換ログを確認。**ベータ専用XCUITestのタブタップ往復は、その後ヘッドレス実Xで2回成功**。なおスワイプ往復の再現性、ショートカット案内との競合は引き続き確認対象。iPhone実機のメモリ負荷・終了挙動、切替速度の実測も未確認。ベータを通常の設定から使える実装にはなったが、PR #9はDraftのままとし、mainへは未統合。

**追加安定化（2026-10-26）：** ベータの非同期先読み処理がバックグラウンド移行後に再実行されないよう、スケジュール時・実行直前・第二WebView生成直前にアプリのactive状態を確認。待機側の`NSURLErrorCancelled`（通常のナビゲーションキャンセル）は致命的な読み込みエラーと扱わないよう修正。修正後もiOS Simulator向けビルド、Playwrightベータブリッジ試験、ログイン済みXでの専用XCUITest（タブタップ往復）が成功。実機のメモリ負荷と連続スワイプ・設定変更時の回帰は未完了。

**操作直後の表示検証（2026-10-26）：** ログイン済みiPhone 17 Pro Simulatorの実XでDEBUG監査を有効にし、ベータONのXCUITest（`For you ↔ Following`往復）が合格。先読み側と元の画面の両方で、切替直前と直後の`performance.timeOrigin`（文書生成時刻）が一致し、投稿要素数も18→18件、25→25件、ページの`readyState=complete`を維持。切替直後に両方向とも402×874のWebKitスナップショットを取得し、XCUITestの直後スクリーンショットでも投稿本文・画像が表示されていることを目視確認。**この条件ではページ全体の再読み込みや白画面待ちは発生していない。** X自体の新着取得XHR等が止まることや、全画像の通信ゼロは保証しない。検証時に戻り側でXのショートカット案内が重なる事例があり、表示品質の回帰課題として残す。Xの新規ナビゲーションで待機側を無効にして、投稿DOMが実在するまで先読み完了扱いしないガードを追加した。スクロール保持の追加XCUITestは操作がプロフィール遷移を発生させて失敗したため、先読みのスクロール保持の合否判定には使用しない。

**実Xページビュー速度のA/B計測（2026-10-26）：** ログイン済みiPhone 17 Pro / iOS 26.4 SimulatorでベータOFF（X標準タブ操作）とベータON（先読み済み第二WebViewとの交換）を交互に起動して比較。それぞれ別起動2セット×10切替、合計20件ずつ有効。計測区間はアプリ内からのプログラムによるタブ切替開始から、通常側では新しい投稿DOMの出現・描画フレームを経て、両側とも`WKWebView.takeSnapshot`成功まで。**通常側の各セット中央値425.7ms・454.5ms、ベータ側56.8ms・56.1ms**。合算中央値は通常436.6ms、ベータ56.35msで**約380ms短縮（87.1%、約7.75倍）**。同一アカウントの実Xだが投稿内容と通信条件は時間で変わる。ベータの準備開始から待機WebViewの投稿描画完了まで別途約4.95秒／5.14秒必要（表示中のページの裏側で実施）。最初の切替は通常1.34秒／2.29秒、ベータ244ms／51ms、ベータ最初の戻りは413ms／424msとばらつく。指のタッチ認識・スワイプアニメーション所要時間は含めず、画像の全リソース転送完了を保証するものでもない。物理iPhoneでの体感速度ではなくSimulator上のアプリ内部＋スナップショット完了時刻であり、計測はDEBUG起動引数`--xtend-benchmark-pageview`で再現できる。

**検証上の追加課題：** 2026-10-26のベータオフでの実X XCUITestでは`For you → Following`は成功、`Following → For you`の戻りスワイプは失敗。既存のタッチ除外判定とその時点の投稿DOMが原因かは未確定。タイムラインの操作対象上から始めたスワイプはそもそも対象外とする現行仕様だが、ユーザーが自然に操作できる座標での再現性を確認すること。ベータオンの実Xはネイティブブリッジ受信・2画面スワップ成功ログを得た一方、キーボードショートカット案内の残留、XCUITestのAXタブ判定差により、タブ往復の自動テストは未合格。

**残り：** 実Xの先読み完了後のページビュー短縮はSimulatorで測定済み。実際の指スワイプから可視フレームまでの動画比較、画像・動画リソースの読み込み状態、スクロール維持、iPhone実機でのメモリ・バッテリー負荷・連続操作安定性は未確認。ベータは初期OFFを維持し、PRはDraftとする。

## 今後追加する拡張機能・操作改善

### 新規 Chrome 拡張機能：タイムラインのアカウント許可リストフィルター

**状態：独立WXT拡張機能として実装・ChromeのモックE2Eまで完了（`../extensions/x-timeline-filter/`）。実際のXでのフィルター操作、実Xリストからの取り込み、Xtend実機への対応は未検証・未実装。**

**目的：** 利用者が端末内に登録したアカウントの投稿だけを X のタイムラインに表示し、それ以外をクライアント側で非表示にする。X のフォロー・ミュート・ブロック・リスト設定そのものは変更しない。

**必須機能（第1段階）**

1. WXT / Manifest V3 ベースの独立した Chrome 拡張機能を作成する。PC の Chrome でまず動作させ、Xtend での利用は別途互換性を検証する。
2. 許可アカウントを **拡張機能専用の `chrome.storage.local`** に永続保存する。X ページの `window.localStorage` に保存しない。アカウントを追加・削除・一覧確認できる。
3. X が通常どおり取得し描画した投稿を、Content Script が DOM 上で判別し、**許可リスト外のアカウントの投稿だけを非表示**にする。通信遮断、取得リクエストの書き換え、X のサーバー側フィルター操作は行わない。
4. ホームの「おすすめ」「フォロー中」を最初の対象にする。追加読み込み、無限スクロール、画面内の仮想化・再描画、タブ切り替え後もフィルターが持続するようにする。通常の投稿の著者を判定し、再投稿では再投稿者でなく **元投稿の著者** を基準にする。引用投稿や複数著者の表示は実画面で挙動を確認し、対象外投稿が露出しない条件を詰める。
5. 拡張機能の設定 UI でフィルターの ON/OFF と、許可アカウントをまとめた **表示グループ（プリセット）の切り替え** を提供する。切り替え時はページ再読み込みなしで表示を再評価する。
6. 通常の閲覧中は、判定・表示制御のための X API 呼び出し、認証情報取得、外部サーバー送信を行わない。不要な権限を要求しない。**「X に絶対検知されない」ことは保証しない** が、フィルタリングを X への追加リクエストやアカウント操作として送らない設計にする。

**追加機能（第2段階、技術検証後）：「X のリスト」から許可アカウントを取り込む**

**実装状況（2026-10-24）：** 表示済みのメンバーをDOMから読み取り、スクロール中に読み込んだ分をタブ内に蓄積してグループに追加する機能を実装。全件自動取得・自動同期は行わない。実Xのリスト画面での取り込みは未検証。

- 利用者が X 上で閲覧できるリストのメンバー情報を元に、許可グループを作成・更新できるようにする。取り込み先を新規グループ／既存グループから選べるようにする。
- 第一候補は、利用者が通常操作で開いたリストの **メンバー画面に表示された情報を読み取り**、端末内へ保存する方式。リスト閲覧に伴う X 本来の通信は発生するが、取り込み専用の非公開 API 呼び出しや大量の自動アクセスを前提にしない。
- X のメンバー画面が遅延読み込み・ページ分割される場合は、**取得件数と未取得の可能性**を明示する。全件取り込みが実現できないのに「同期完了」とは表示しない。
- リストへの加入・離脱や X 側の設定を変更する機能ではなく、あくまでローカルへの取り込み。取り込んだグループの切り替えは X に通知しない。自動同期の導入は別途判断する。
- リスト取り込みが DOM 制約等で安定しない場合も、手動追加とローカルグループ切り替えは独立して利用可能にする。

**実装前に確認すること**

- 実際の X の DOM と SPA 遷移、ポスト・再投稿・引用の著者識別方法、動的 DOM 監視の性能。X 側の変更で誤非表示が起こった場合に、すぐ OFF に戻せること。
- WXT の Content Script と `chrome.storage.local` の利用が、PC Chrome と Xtend の限定的 Chrome API 実装の双方で成立するか。Xtend は現状インストール対象を限定しているため、**この新拡張機能を認識・インストール・起動する Xtend 側の対応も別タスク**とする（Phase 2 の「汎用拡張機能対応」には含めない）。
- X のリスト画面でメンバーが全件取得可能か、非公開リストへのアクセス権限の扱い、メンバー数が多い場合の欠落や重複。

**完了条件**

- Chrome で登録済みアカウントの通常投稿は表示され、未登録アカウントの通常投稿は表示されない。無限スクロール・タブ移動・新着更新・グループ切り替え後も動作し、表示設定は再起動後も保持される。
- フィルター ON/OFF やグループ切り替えで、X 側への追加のフィルター通信やフォロー・ミュート・ブロック操作が発生しないことを通信ログ等で検証する。通常の X 閲覧通信そのものは止めない。
- リスト取り込みを実装した場合は、画面上で確認可能なメンバーと取り込み結果を照合し、未取得分を検出・表示する。拡張機能と Xtend 本体の動作検証結果は分けて記録する。
