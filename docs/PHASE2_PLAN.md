## 目的と範囲

**目的**：現在の「iPhoneでXを閲覧し、対応するChrome拡張機能を動かすX専用アプリ」という製品方針のまま、障害からの復旧、拡張機能操作の確実性、閲覧継続性を改善する。

**Phase 2完了の判定**：

1. 拡張機能が未導入・破損・互換性不足でも、壊れた拡張機能だけを無効化してXの閲覧と修復操作を継続できる。ログイン状態や保存設定を勝手に破壊しない。
2. インストール・更新・削除で既存の正常な拡張機能が意図せず壊れず、失敗時は明示的なエラー表示と安全な復元経路がある。
3. にゃっとランドの設定変更を端末内に保存し、Xを再読み込みすれば反映できる。設定変更の即時反映は必須条件にしない（2026-10-25に範囲を明確化）。
4. 拡張機能の追加・更新・削除に成功したら、ユーザーの手動操作なしに自動再読み込みで反映する。失敗・キャンセル時は不必要に再読み込みしない。
5. 拡張機能構成の変更でWebViewを再生成する場合、閲覧中のURLを維持する。独自のスクロール位置・ポスト位置の復元は行わず、再読み込み後もXを正常に操作できる。
6. 指定した単体・統合テスト、Simulator上の確認、**実機での手動スモークテスト**をそれぞれ区別して完了する。

**範囲外**：汎用ブラウザ化、未対応のChrome拡張機能の追加、Chrome API全実装、拡張機能自動更新、App Store/TestFlight配布、新しい分析サーバー、アカウント機能、既存XログインのGoogle OAuth制約の解消、x-home-anchor自身の「新しいポストを表示」後の位置維持品質。Phase 3/4の作業を先取りしない。

## 確定した製品方針（2026-10-24更新）

1. **破損した拡張機能だけを無効化し、X閲覧を続ける。** 正常な拡張機能の機能を維持し、設定画面から不具合のある拡張機能を修復できるようにする。X全体を停止する案は不採用。ファイルや端末内設定の自動削除もしない。
2. **Xtend独自のスクロール位置復元は行わない。** Xの動的タイムラインでは同じスクロール量でも同じポストに戻らないため、複雑な位置取得・DOMアンカー照合・再試行は不要と判断。拡張機能構成変更後はURLのみ引き継ぐ。x-home-anchorによるX内部の「新しいポストを表示」の位置補助は別機能として維持する。
3. **拡張機能の追加・更新・削除が成功したら自動再読み込みする。** ユーザーに手動の「Xのページを再読み込み」を要求しない。設定画面での複数操作はまとめ、閲覧画面に戻るときに最新の拡張機能構成を1回だけ反映し、URLのみ引き継ぐ。初回ウェルカム画面では初回ブラウザ生成時に反映し、二重読み込みをしない。失敗・キャンセル時は再読み込みしない。既存の手動再読み込みは補助的な復旧操作として残せる。

判断変更の背景は[ADR 0002](adr/0002-simple-extension-reload.md)を参照する（[旧ADR 0001](adr/0001-phase2-extension-recovery.md)を置き換え）。

自動再読み込みでは閲覧位置・未送信入力・メディア再生状態が失われる。拡張機能構成が変わったときだけ再構築し、回数を最小化する。**拡張機能の設定値変更（popupでの保存）**は既存のT-04変更通知を維持するが、個々の拡張機能が通知を処理してXへ即時反映することまでは保証しない。必要な場合は既存の「Xのページを再読み込み」で反映する。設定値の変更だけでWebViewを自動再構築しない。

## 実装順序・タスク・完了条件

### M0：再現・回帰検証の最小基盤（先行）

**T-00 テスト基盤を作る**
- `project.yml`に必要最小限のXCTestターゲットを追加する。専用CI/GitHub Actionsや汎用モックフレームワークを増やさない。
- テスト対象：破損manifest、必要リソース欠落、ZIPの不正パス・過大ファイル・symlink、失敗時の旧版維持、保存領域の分離と通知、変更成功時だけの自動再読み込み、URLの維持。
- 外部拡張機能の実ファイルやログイン情報は同梱しない。テスト専用の小さな合成fixtureを使う。
- 完了：少なくとも重要な失敗経路が自動テストで再現でき、クリーンビルドとテスト実行手順が`DEVELOPMENT.md`に残る。

### M1：起動不能・更新破損を防ぐ（最優先）

**T-01 障害を起こした拡張機能を隔離し、Xを閲覧可能にする**（R-01/R-07）
- ランタイム読み込みを拡張機能ごとに失敗分離する。健全な拡張機能は継続、壊れた拡張機能だけ読み込まない。
- ブラウザ画面の起動と設定への導線を、拡張機能ロードの成功に依存させない。
- 設定画面には読み込めないインストール済みの拡張機能を「要修復」として表示し、明示的な削除・再インストール手段を設ける。ファイルと拡張機能設定を勝手に削除しない。
- ログインCookieとWebKitデータストアは触らない。ユーザーへ障害の原因を短く伝える。
- 完了：破損したにゃっとランド、破損x-home-anchor、それぞれ単独・同時のケースでXへ進め、設定画面に到達し、正常な方が動作し続ける。復旧後にもログイン状態が維持される。

**T-02 インストール事前検証・ロールバックの強化**（R-04/R-06）
- インストール前に、現行ランタイムが**必ず使う**リソースを検証する（実際に使用する`popup.html`、`xff-assets.js`、インデックス形式・参照pack、各content script等）。現行の2拡張機能の契約に限定し、汎用拡張機能検証器に肥大化させない。
- 新パッケージの検証・必要な起動前チェックを通してから差し替える。保存済み設定や正常な現行版は失敗時に維持。
- 旧版退避・書き戻しの失敗を明示的に検出し、復旧可能な退避ファイルを消さず、修復UIへつなげる。途中終了時の残骸処理と再起動後の復旧をテストする。
- 完了：欠損・形式不正・予期せぬ更新中断のfixtureを拒否し、旧版のファイルと設定が維持される。更新成功後の起動時に同じ前提条件で失敗しない。

### M2：設定の整合性と操作の応答性

**T-03 導入・更新処理のノンブロッキング化**（R-05）
- ダウンロードをファイルベースにし、受信途中もサイズ上限を強制する。ZIP/CRXの重い検証・展開をメインスレッドから外す。UI反映だけMainActorに戻す。
- 導入・更新の並行実行を同一拡張機能IDについて直列化。画面を閉じる・キャンセルする際の処理ルールを一本化し、途中更新を壊さない。
- 現在のサイズ・エントリ数・展開サイズ制限は維持する。実態に応じて上限を再評価し、緩和だけを目的に変更しない。
- 完了：上限超過が保存前に拒否され、重い処理中もボタン・スクロール等の画面応答が維持される。競合する2件の更新でも正常な最終状態に落ち着く。

**T-04 拡張機能設定の変更通知を接続する**（R-02）
- `ExtensionStorage`インスタンスの同一性に頼らず、拡張機能ID・保存領域で通知をルーティングする。ブラウザとpopupの両方向で`chrome.storage.onChanged`を伝える。
- 同じ拡張機能の値は共有し、異なる拡張機能の通知は絶対に混ぜない。1回の変更が重複して通知されないようにする。
- 完了：拡張機能ID別の保存・通知が働き、アプリ再起動後に値が保持され、Xの再読み込み後に設定を再適用できる。表示中のXへの即時反映は拡張機能自身の実装次第で、Xtendの必須条件にしない。設定変更のみでWebViewを自動再構築しない。

### M3：閲覧継続性とエラー復旧

**T-05 拡張機能変更後の自動再読み込み（URLのみ継続）**
- 拡張機能の追加・更新・削除が成功した場合だけ、構成変更を記録する。設定画面を閉じるときに変更をまとめて1回だけ反映する。失敗・キャンセルでは再構築しない。
- 変更した拡張機能のcontent scriptsを反映するため、必要なときは新しいWebViewを生成し、現在のURLを読み込む。設定値の変更だけならWebViewは維持する。
- Xtend独自のスクロール位置・表示ポストの採取や復元処理は行わない。これを確認するためだけの視覚的スクロール一致テストも対象外。
- 初回ウェルカム画面での導入は初回ブラウザ生成で反映し、二重読み込みをしない。手動再読み込みは補助的な復旧手段として残す。
- 完了：追加・更新・削除成功後は手動操作なしに反映され、画面は元のURLで正常に表示される。失敗・キャンセル時はX表示が不用意に再生成されない。
**T-06 ナビゲーションの失敗時UI**（R-08）
- Xのページ読込失敗を識別し、具体的なエラーと再試行ボタンを用意する。
- WebContent process終了時の再読み込みが連続する場合は無制限のループを避け、ユーザー操作で再試行できる状態に移す。
- 完了：オフライン、タイムアウト、WebContent終了を試験し、操作導線とログインCookieが保たれる。

**T-07 入力・案内の細部の整合**（R-09）
- Chrome Web StoreのURLと既知の拡張機能IDのみを受け付けるよう、入力形式を現行UIの説明と一致させる。
- インストール中の閉じる・削除操作の状態表示を整える。成功した構成変更は閲覧画面に戻るとき自動反映することを表示し、手動再読み込みを必須手順として案内しない。
- 完了：Store以外の紛らわしいURLが明示的に拒否され、拡張機能変更後の再読み込み操作をユーザーに要求しない。

## 実行順序と依存関係

`T-00`（最小テスト基盤）→ `T-01`（起動復旧）→ `T-02`（事前検証とrollback）→ `T-03/T-04`（導入処理と変更通知、相互に独立）→ `T-05/T-06`（閲覧・エラー復旧）→ `T-07`（入力・案内）→ `T-08`（統合確認）。

- 起動復旧とインストール検証は最初に扱う。データや閲覧が失われるケースを先に潰す。
- `T-04`は比較的独立して先行も可能。`T-05`は`T-01`の起動・復旧方式を踏まえて着手し、`T-03`の成功通知から自動反映する。
- 新しい共通フレームワークを増やさず、既存の`ExtensionRuntime` / `ExtensionInstallStore` / `ExtensionStorage` / `BrowserViewController`を中心に変更。
- 各タスクは自動テストまたは実機検証のうち可能なものを添えて個別コミットする。完了の定義は実装・テスト・体験確認を区別する。
